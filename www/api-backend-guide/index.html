The api.pimenta.fun backend service

A long-running REST API (Express + SQLite) that powers the shop and the API console. This guide explains how the request path works end-to-end and walks through deploying it as an always-on, auto-restarting systemd service behind Apache.

1. Architecture

The public hostname api.pimenta.fun is fronted by Cloudflare and served by Apache on the origin. Apache does two jobs: it serves the static API console at /, and it reverse-proxies the API paths to a Node/Express service bound to 127.0.0.1:3000, which reads and writes a file-based SQLite database.

EDGE

Cloudflare

Terminates TLS, applies WAF/bot rules and caching, then forwards to the origin.

ORIGIN

Apache

Serves the static console and reverse-proxies API paths to the local Node service.

APP

Node / Express

Implements the REST routes, JWT auth and business logic. Never exposed directly.

DATA

SQLite (WAL)

File-based DB at /var/lib/pimenta-api/pimenta.db; persists across reboots.

2. Request routing

Apache decides per path whether to answer from disk or hand off to the backend. This split is the whole trick — and the usual failure point (see Troubleshooting).

GET /
→ DocumentRoot /var/www/pimenta/api — static console (index.html)
/rest/*   /api/*   /health
→ ProxyPass to http://127.0.0.1:3000 — the Node backend
Why this matters If the ProxyPass rules are not active, Apache tries to serve /rest/… from disk, finds no file, and returns its own 404 (an ISO-8859-1 HTML page that says Apache/2.4 … Server at api.pimenta.fun). That is the signature of a broken proxy — not a backend crash.

3. JWT auth flow

Passwords are bcrypt-hashed; a successful login returns a signed JWT shaped like OWASP Juice Shop's response, so the console auto-captures the token and replays it as Authorization: Bearer <token> on protected routes.

# 1) Login and capture the token
TOKEN=$(curl -s https://api.pimenta.fun/rest/user/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@juice-sh.op","password":"admin123"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["authentication"]["token"])')

# 2) Call a protected route with it
curl -s https://api.pimenta.fun/rest/user/whoami -H "Authorization: Bearer $TOKEN"

5. Repo layout

Everything the service needs lives in backend/:

backend/ ├── server.js # Express app + all routes ├── db.js # SQLite schema + seed (products, admin user) ├── package.json ├── pimenta-api.service # systemd unit (Restart=always, start on boot) └── pimenta-api.env.example # config template (port, JWT secret, DB path)

6. Deploy step-by-step

Run these on the origin server, from the repo's backend/ directory. This is the exact sequence that turns a fresh box into a running API.

  1. Install Node.js 20 + build tools

    better-sqlite3 compiles a native module, so build tools are required.

    curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs build-essential python3

  2. Create the service user & app directory

    sudo useradd --system --home /opt/pimenta-api --shell /usr/sbin/nologin pimenta || true
sudo mkdir -p /opt/pimenta-api
sudo cp -r server.js db.js package.json /opt/pimenta-api/
sudo npm --prefix /opt/pimenta-api install --omit=dev
sudo chown -R pimenta:pimenta /opt/pimenta-api

  3. Create the persistent database directory

    sudo mkdir -p /var/lib/pimenta-api
sudo chown pimenta:pimenta /var/lib/pimenta-api

  4. Write the config (env file)

    Generate a strong JWT secret and set the admin password before going public.

    sudo mkdir -p /etc/pimenta-api
sudo cp pimenta-api.env.example /etc/pimenta-api/pimenta-api.env
sudo sed -i "s|replace-with-openssl-rand-hex-32|$(openssl rand -hex 32)|" /etc/pimenta-api/pimenta-api.env
sudo nano /etc/pimenta-api/pimenta-api.env      # set ADMIN_PASSWORD, CORS_ORIGINS
sudo chmod 600 /etc/pimenta-api/pimenta-api.env

  5. Install & start the systemd unit

    This is the step whose absence produces Unit pimenta-api.service could not be found.

    sudo cp pimenta-api.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now pimenta-api          # enable = start on boot
sudo systemctl status pimenta-api                # -> active (running)

  6. Verify it's alive

    curl -s http://127.0.0.1:3000/health            # -> {"status":"ok",...}
curl -s https://api.pimenta.fun/health          # same JSON = proxy + backend OK
tools/smoke-test.sh https://api.pimenta.fun     # asserts every route (exit 0 = all pass)
Config reference HOST=127.0.0.1, PORT=3000, JWT_SECRET, JWT_TTL=2h, DB_PATH=/var/lib/pimenta-api/pimenta.db, ADMIN_EMAIL/ADMIN_PASSWORD (seed admin, created only if the users table is empty), CORS_ORIGINS.

7. Apache reverse proxy

The api.pimenta.fun vhost keeps the console at / and forwards the API paths to the backend. Enable the proxy modules and load the vhost:

sudo a2enmod ssl headers rewrite proxy proxy_http socache_shmcb
sudo cp apache/api.pimenta.fun.conf /etc/apache2/sites-available/
sudo a2ensite api.pimenta.fun.conf
sudo apache2ctl configtest && sudo systemctl reload apache2

The relevant directives inside the :443 vhost:

DocumentRoot /var/www/pimenta/api          # static console at "/"

ProxyPreserveHost On
ProxyRequests Off
ProxyPass        /rest/   http://127.0.0.1:3000/rest/
ProxyPassReverse /rest/   http://127.0.0.1:3000/rest/
ProxyPass        /api/    http://127.0.0.1:3000/api/
ProxyPassReverse /api/    http://127.0.0.1:3000/api/
ProxyPass        /health  http://127.0.0.1:3000/health
ProxyPassReverse /health  http://127.0.0.1:3000/health
One command for everything apache/enable-sites.sh enables the modules, installs all four vhosts, runs configtest and reloads — use it instead of the manual steps above.

8. Always-on (systemd)

The unit guarantees the API keeps running across crashes and reboots.

  • Restart=always + RestartSec=3 — if node exits for any reason, systemd relaunches it after 3 seconds.
  • StartLimitIntervalSec=0 — systemd never gives up restarting.
  • WantedBy=multi-user.target + enable — starts automatically on every boot/reboot.
  • StateDirectory=pimenta-api — /var/lib/pimenta-api persists, so the DB survives restarts.
# Prove it: kill it and watch systemd bring it back
sudo systemctl kill -s SIGKILL pimenta-api
sleep 4 && systemctl status pimenta-api          # active (running) again

9. CORS & port note

Port 3000 conflict This API and OWASP Juice Shop both default to 3000 — run only one on that port. To run both, set PORT=3001 in the env file and point a separate vhost at it.

The shop/www pages call this API cross-origin, so their domains must be allowed via CORS_ORIGINS (default https://www.pimenta.fun,https://shop.pimenta.fun,https://api.pimenta.fun). Requests with no Origin header (curl, server-to-server) are always allowed. Add http://localhost:8080 when testing a frontend locally.

10. Operations

sudo systemctl restart pimenta-api      # manual restart
sudo systemctl stop pimenta-api         # stop
sudo systemctl disable pimenta-api      # don't start on boot
journalctl -u pimenta-api -f            # live logs

# Re-seed / inspect the database
sudo -u pimenta DB_PATH=/var/lib/pimenta-api/pimenta.db node /opt/pimenta-api/db.js --seed
sudo -u pimenta sqlite3 /var/lib/pimenta-api/pimenta.db ".tables"

# Backup
sudo cp /var/lib/pimenta-api/pimenta.db ~/pimenta-backup-$(date +%F).db

11. Troubleshooting

SymptomCauseFix
API paths return an Apache HTML 404 (charset=iso-8859-1, "Server at api.pimenta.fun") Reverse proxy not active — Apache is serving /rest from disk. Enable proxy/proxy_http, (re)deploy the vhost, reload Apache. See §7.
Unit pimenta-api.service could not be found The backend was never installed as a service. Run the deploy steps — specifically step 5.
502 / 503 Bad Gateway from the API paths Proxy is active but the backend is down or not listening on 3000. systemctl status pimenta-api; curl 127.0.0.1:3000/health; check journalctl -u pimenta-api -e.
Service crash-loops right after start Bad env file path/permissions, unwritable DB dir, or the native better-sqlite3 build failed. Confirm /etc/pimenta-api/pimenta-api.env (chmod 600), owner of /var/lib/pimenta-api, and that build-essential python3 are installed.
Browser calls blocked by CORS The calling origin isn't in CORS_ORIGINS. Add the origin to the env file and restart the service.
