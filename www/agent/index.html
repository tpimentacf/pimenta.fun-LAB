AI Agent

Cloudflare AI Chat Agent

A chat agent running on Cloudflare Workers, connected to the pimenta-ai-mcp server. Ask it something and it decides whether to answer directly or call one of the MCP server’s tools — notes (D1), key/value (KV), or ask_ai (Workers AI) — then feeds the result back and replies. Powered by Workers AI function calling.

Heads up: This agent and the MCP server it calls are unauthenticated demos. Notes and KV values you create here are shared lab data — don’t store anything sensitive.

How it works

The agent is the MCP client; the MCP server owns the data. One user message can trigger several tool calls before the final answer.
   you
    │  message
    ▼
 ┌──────────────────────────── ai-agent Worker ────────────────────────────┐
 │  Workers AI  (llama-3.3-70b, function calling)                           │
 │      │  answer? ──────────────────────────────────────────────► reply   │
 │      │  tool_call?                                          ▲            │
 │      ▼                                                      │ result     │
 │  MCP  tools/call  ───►  https://www.pimenta.fun/mcp  ───►  D1 / KV / AI  │
 │      └──────────────────────── feed result back, loop ──────┘            │
 └──────────────────────────────────────────────────────────────────────────┘

  1. Discover tools

    On each turn the agent does an MCP initialize + tools/list against the server, then maps every tool’s JSON-Schema inputSchema into the Workers AI tools format.

  2. Let the model decide

    env.AI.run(model, { messages, tools }) either returns text (done) or a tool_calls array naming a tool and its arguments.

  3. Call the tool over MCP

    For each requested tool the agent sends tools/call to the MCP server (Streamable HTTP, SSE-framed), reads the text result, and appends it as a tool message.

  4. Loop, then answer

    Repeat until the model stops calling tools (capped by MAX_STEPS). Its final text is the reply; the tool trail is shown under each answer.

Tools it can call

Exposed by the pimenta-ai-mcp server — the agent chooses among these automatically.

Testing PII protection

The dashed Test… chips send prompts containing synthetic personal data.

Every model call the agent makes — both its own reasoning turn and the ask_ai tool — is routed through the pimenta-lab AI Gateway. AI Gateway Guardrails can inspect prompts and responses and detect / block PII (emails, phone numbers, SSNs, payment cards, IBANs, and more). These chips let you see that in action:

  • With Guardrails off: the prompt flows straight through — a good reminder not to store real PII in demo notes.
  • With Guardrails set to flag: the request still runs, but the gateway logs mark the detected PII categories.
  • With Guardrails set to block (currently on for this lab): the gateway rejects the call before it reaches the model (error 2016), and the agent shows a 🎡️ “blocked” message — that block is the protection working. Nothing sensitive ever reaches the model.

Configured in AI → AI Gateway → pimenta-lab → Guardrails (here: PII / Privacy set to block on prompts). All chip data above is fake test data — never paste real personal information.

Build & deploy

The Worker lives in workers/ai-agent/. It needs only the Workers AI binding — D1 and KV stay on the MCP server.

  1. Make sure the MCP server is deployed

    The agent calls MCP_URL (default https://www.pimenta.fun/mcp), served by workers/ai-mcp. Deploy that first.

  2. Install & deploy the agent

    workers/ai-agent/
    cd workers/ai-agent
npm install
npx wrangler deploy

    The route www.pimenta.fun/agent/api and the AI binding come from wrangler.jsonc.

  3. Test the endpoint

    curl -sS https://www.pimenta.fun/agent/api \
  -H 'content-type: application/json' \
  -d '{"messages":[{"role":"user","content":"list my notes"}]}'

    A plain GET on the same URL returns a small JSON probe (service, MCP URL, model).
