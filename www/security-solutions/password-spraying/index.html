Password Spraying Protection

Password spraying tries a few common passwords against many accounts to stay under per-account lockout thresholds — often from many IPs. The credentials arrive in the request body, so the defence has to inspect the POST body, not just the URL. This is how Cloudflare stops it, layer by layer.

The credentials are submitted in the body, e.g. --data-raw 'username=user%40example.com&password=Winter2025'. Every rule below keys off http.request.body.form[…] (URL-encoded) or lookup_json_string() (JSON).

Spraying vs. brute force vs. stuffing

AttackPatternWhy lockouts miss it
Brute forceMany passwords vs. one accountPer-account lockout catches it fast.
Password sprayingFew common passwords vs. many accountsOnly 1–2 tries per account — under the lockout threshold.
Credential stuffingLeaked user:pass pairs replayedEach pair tried once; looks like normal logins.

The through-line: rate limiting by IP alone is not enough. Effective defence tracks the account being targeted, scores automation, and checks whether the password itself is already compromised.

1

Advanced Rate Limiting — per-username

Enterprise + Advanced Rate Limiting

Rate limit by the username value extracted from the body, not the client IP. This is the single most important control: it catches distributed spraying where each IP only sends a request or two, but the same account is hammered from all of them.

Rule expression (when to count)
# POST to the login endpoint that carries a password
http.request.uri.path eq "/login" and
http.request.method eq "POST" and
http.request.body.form["password"] ne ""
Counting characteristic (track the rate per account)
http.request.body.form["username"]

Tune: e.g. 5 requests / 10 minutes per username, action Managed Challenge (softer) or Block. Add a second rule counting per IP as a backstop. For JSON logins, count on lookup_json_string(http.request.body.raw, "username").

2

Bot Management — block automation

Enterprise + Bot Management

Spraying is almost always automated (hydra, Burp Intruder, scripted curl loops, headless browsers). Bot Management scores every request 1–99 (1 = certainly a bot, 99 = certainly human). Challenge or block low scores at the login endpoint.

# Challenge automated requests hitting the login page
http.request.uri.path eq "/login" and
cf.bot_management.score lt 30

Prefer Managed Challenge over Block for the 1–30 band to avoid blocking real users on shared networks; reserve hard Block for very low scores or combine with Layer 1/4 signals. verified_bot traffic (uptime monitors, etc.) can be allowed explicitly.

3

WAF custom rules — body inspection

Pro / Business (limited) Enterprise (full body)

Inspect the body to block malformed logins and obviously scripted shapes — a cheap first filter that runs before the heavier layers.

Block malformed requests (missing password field)
http.request.uri.path eq "/login" and
http.request.method eq "POST" and
not http.request.body.form["password"] ne ""
Match a weak / templated password format with regex
# Example: exactly 8 lowercase-alnum chars — a common generated pattern
http.request.uri.path eq "/login" and
http.request.body.form["password"] matches "^[a-z0-9]{8}$"

Use pattern rules sparingly — they are easy to evade and can cause false positives. Treat them as signals feeding a challenge, not a sole defence.

4

Leaked Credential Check (LCC)

Enterprise WAF add-on · the strongest single signal

Cloudflare checks submitted credentials against known-breached databases in-line, exposing the result as cf.waf.credential_check.* fields you can act on — without your origin ever handling the raw comparison.

Challenge logins using a known-leaked password
http.request.uri.path eq "/login" and
cf.waf.credential_check.password_leaked eq true
Highest confidence — the exact user:pass pair is known-breached
cf.waf.credential_check.username_and_password_leaked eq true
  • password_leaked — the submitted password appears in a breach set.
  • username_and_password_leaked — the exact pair is known-compromised (block outright).
  • username_leaked, similar_password — weaker signals for step-up auth.

Best practice: don’t just block — on a leaked match, force MFA / password reset so you also protect the legitimate owner of a compromised credential.

5

Turnstile & Access — raise the cost

All plans (Turnstile free)

Beyond detection, make automation expensive up front:

  • Turnstile on the login form issues a token the backend validates — with pre-clearance it also sets cf_clearance, so a WAF rule can require a valid challenge before /login is even reachable.
  • Cloudflare Access in front of admin / internal logins removes password auth from the public Internet entirely (SSO + device posture).
  • Account-based rate limiting + progressive delay at the origin (e.g. Worker + KV) as a backstop for the account being targeted.

Recommended layered approach

Defence in depth — each layer catches what the others miss. Run them log-only first, then enforce.

LayerCatchesSuggested actionPlan
1 · Rate limit / usernameVolume & distributed spraying on one accountManaged Challenge → BlockEnt + Adv RL
2 · Bot ManagementAutomated tools, scripts, headlessChallenge low scoresEnt + Bot Mgmt
3 · WAF custom rulesMalformed / templated requestsBlock obvious, else signalPro / Biz / Ent
4 · Leaked Credential CheckBreached passwords & pairsBlock pair; MFA on passwordEnt WAF add-on
5 · Turnstile / AccessBulk automation up frontRequire token / SSOAll / Zero Trust
Best combined rule of thumb: hard-block only on high-confidence signals (username_and_password_leaked, bot score < 5). For everything else, challenge and let real users through — then watch Security Analytics and tighten. This minimises false positives while still shutting down the spray.

Key fields for a form body

For application/x-www-form-urlencoded; use lookup_json_string(http.request.body.raw, "field") for JSON.

FieldWhat it is
http.request.body.form["username"]The username POST parameter — use as the rate-limit characteristic to track per-account attempts.
http.request.body.form["password"]The password parameter — match, inspect, or pattern-match the submitted value.
http.request.body.rawRaw body string — for custom parsing or non-standard encodings / JSON.
cf.bot_management.scoreBot score 1–99 (1 = certainly automated). Requires Bot Management.
cf.waf.credential_check.password_leakedBoolean — true if the submitted password matches a breached-credential entry.
cf.waf.credential_check.username_and_password_leakedBoolean — true if the exact user:pass pair is known-breached.

Body fields require the rule to run on requests with a parsed body — scope to POST on the login path. Full raw-body inspection is an Enterprise capability.

Test it

Simulate a spray and confirm the layers fire in Security Analytics / the rule’s log.

# A crude spray: one common password across many usernames
for u in alice bob carol dave erin; do
  curl -s -o /dev/null -w "%{http_code}\n" https://www.pimenta.fun/login \
    -X POST \
    --data-raw "username=${u}@example.com&password=Winter2025"
done

# Expect: first few 200/401 from origin, then 403 (Block) or 429
# (Rate Limiting) / a challenge interstitial once a layer trips.
  • Watch Security → Analytics — events attributed to Rate Limiting, Bot Management, WAF, or Leaked Credentials.
  • Deploy each rule in Log mode first to size false positives before switching to Challenge/Block.
Only test against endpoints you own. These examples target this lab’s own login path for demonstration.
