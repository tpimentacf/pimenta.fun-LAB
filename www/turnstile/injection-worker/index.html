Turnstile

Turnstile Injection & Verification Worker

A Cloudflare Worker that sits in front of your origin, injects the Turnstile widget into your HTML on the fly (no origin code changes), and verifies the token server-side before any form submission is allowed to reach the origin.

The big idea: your origin never has to know about Turnstile. The Worker adds the challenge to outgoing pages and enforces it on incoming submissions — ideal for legacy apps, third-party platforms, or anywhere you can’t easily edit the backend.

Three jobs, all at the edge

🧩

Inject

Uses HTMLRewriter to stream the API script into <head> and a widget into your forms.

🛡

Verify

Intercepts POSTs, validates the token at /siteverify, and blocks failures with 403.

⚡

Zero origin changes

All logic lives at the edge. The origin serves plain HTML and receives only verified traffic.

How it works

The Worker’s fetch handler branches on the HTTP method. Mutating methods (default POST) go through verification; everything else is proxied and rewritten.

export default {
  async fetch(request, env, ctx) {
    const verifyMethods = (env.VERIFY_METHODS || "POST").split(",")...

    // 1. Mutating request? Verify Turnstile BEFORE touching origin.
    if (verifyMethods.includes(request.method.toUpperCase())) {
      return handleVerifiedSubmission(request, env, ctx);
    }

    // 2. Otherwise: proxy to origin + inject Turnstile into HTML.
    const originResponse = await fetchOrigin(request, env);
    ...
  }
};

Why HTMLRewriter? It streams — the page starts sending to the browser immediately without buffering the whole body in memory, so injection adds near-zero latency.

const token = await extractToken(request.clone());

Token extraction supports three body types
  • application/x-www-form-urlencoded — classic HTML forms
  • multipart/form-data — forms with file uploads
  • application/json — reads cf-turnstile-response or token

Implement it

  1. Get your Turnstile keys

    Dashboard → Turnstile → create a widget. Copy the Site Key (public) and Secret Key (private).

  2. Set the site key

    [vars]
TURNSTILE_SITEKEY = "0x4AAAAAAA_your_real_sitekey"
INJECT_SELECTOR   = "form"
VERIFY_METHODS    = "POST"
# ORIGIN_URL = "https://origin.example.com"

  3. Store the secret (never in the repo)

    # production secret
npx wrangler secret put TURNSTILE_SECRET

# local dev secret
cp .dev.vars.example .dev.vars   # then edit TURNSTILE_SECRET

  4. Point the Worker at your zone

    [[routes]]
pattern   = "example.com/*"
zone_name = "example.com"

  5. Deploy

    npx wrangler deploy

    Load a page on your domain — the widget appears inside your forms and submissions now pass through server-side verification.

  6. Cover every form endpoint

    Make sure every form-handling path is covered by the Worker route and included in VERIFY_METHODS. If a form posts to a different path/subdomain, the route must cover it too, or that submission bypasses verification.

Anti-bypass hardening

A valid Turnstile token is necessary but not sufficient. Solver / “Turnstile bypass” services farm real tokens on hosting infrastructure and replay them. The strongest defence is to check multiple signals and validate the full siteverify outcome — not just success.

The #1 real-world signal: tokenIP ≠ remoteIP. Solvers mint tokens on hosting-provider IPs that differ from the eyeball’s IP. Always send remoteip (the Worker passes CF-Connecting-IP) so Cloudflare can compare token IP vs request IP.
Signal / checkHow it worksEnable with
Full outcomeAfter success, also require matching hostname, action, optional cdata, and a fresh challenge_ts. Stops harvested / replayed / cross-site tokens.EXPECTED_HOSTNAMES, EXPECTED_ACTION, EXPECTED_CDATA, MAX_TOKEN_AGE_SECONDS

Defence in depth beyond the Worker. Complement code-level checks at the platform: a WAF Managed Challenge + pre-clearance on sensitive endpoints (keep Challenge Passage short and rate-limit on the cf_clearance cookie); a hostname allowlist in the Turnstile dashboard; tiered Bot Management; and Rate Limiting on the submit path.

Gotchas & production notes

Verification is what protects you — not the widget. The injected widget is only a UI element. The security comes from the server-side /siteverify check. Never skip it or trust the client.
  • Single-use tokens: Turnstile tokens are consumed on verify and expire after ~300s; the client widget auto-refreshes if the user idles.
  • Body is read once: the Worker uses request.clone() — the clone is read for the token, the untouched original is forwarded to origin.
  • Anti-replay: a stable idempotency_key = sha256(token) is sent (a random UUID would defeat single-use), and an optional TOKEN_REPLAY KV cache rejects any token already spent.
  • Client IP: CF-Connecting-IP is passed as remoteip to harden verification.
  • Non-HTML untouched: only text/html responses are rewritten, so assets and APIs are unaffected.
