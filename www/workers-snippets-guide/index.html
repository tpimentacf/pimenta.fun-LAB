Decision Guide

Cloudflare Workers vs Snippets

Both run JavaScript on Cloudflare's network, but they solve different problems. This guide explains the boundaries, current limits, best use cases, and the simplest way to choose the right product.

0. The short answer

Choose Snippets

Lightweight HTTP middleware

Use a Snippet when a Rules expression selects the traffic and small JavaScript logic modifies the request, origin fetch, cache behavior, or response. No state, bindings, background work, or application platform required.

Rules + short JavaScript
Choose Workers

Applications and platform compute

Use a Worker for APIs, full responses, authentication services, storage, state, queues, scheduled tasks, AI, image processing, larger dependencies, observability, and software delivery workflows.

Full developer platform
Use the lowest abstraction that solves the problem. First ask whether a native Redirect, Transform, Cache, Configuration, or Origin Rule can do it without code. If not, use a Snippet for lightweight request/response logic. Move to Workers when the workload becomes an application.

1. Where they run

Snippets: code inside the Rules pipeline

Incoming request
proxied DNS hostname
→
Ruleset expression
URI, headers, cookies, IP, bot/WAF scores, lists
→
Snippet(s)
small, sequential request/response logic
→
Origin / response
fetch, modify, return

Each Snippet has one associated Snippet rule. Only matching requests invoke it. Multiple matching Snippets can run sequentially, so one can modify the request or response passed to the next. In the Rules execution order, Snippets run after Cache Rules and before Cloud Connector.

Workers: a programmable application endpoint

Event / request
route, custom domain, cron, queue, email, service binding
→
Worker
application logic, routing, APIs, rendering
→
Bindings
KV, D1, R2, Durable Objects, Queues, AI, services
→
Response / workflow
origin optional

A Worker can proxy an origin, but it does not need one. It can be the application, API, scheduled process, queue consumer, or coordination layer itself.

3. Best use cases for Snippets

01

Advanced header logic

Set, remove, or compute request/response headers when a Transform Rule expression alone is not enough.

02

Complex redirects and rewrites

Conditional URL normalization, locale routing, legacy migration behavior, or a response that needs JavaScript logic.

03

Origin routing and retry

Select or retry an upstream based on request attributes or an upstream response, within the tight subrequest limit.

04

Stateless authentication

Validate a JWT or enforce a small request gate without sessions, databases, or persistent state.

05

Cache customization

Apply a small custom caching strategy or response transformation after Cache Rules need additional logic.

06

CDN code migration

Replace lightweight VCL, EdgeWorkers, or appliance logic while keeping traffic selection in the Ruleset Engine.

07

A/B routing

Choose a variant from a cookie, header, country, or request attribute when the decision is stateless.

08

Small custom responses

Return a maintenance, denial, redirect, or diagnostic response for precisely matched traffic.

Do not use Snippets for session state, databases, long loops, heavy parsing, AI inference, image processing, large dependencies, many subrequests, scheduled jobs, or workloads that need rich logs and traces.

4. Best use cases for Workers

01

APIs and full applications

Build an API, backend-for-frontend, static/SSR site, webhook endpoint, or originless service.

02

State and storage

Use KV, D1, R2, Durable Objects, or Hyperdrive for configuration, SQL data, objects, coordination, and database access.

03

Authentication systems

Implement sessions, OAuth/OIDC callbacks, policy engines, token storage, and user-specific authorization.

04

Background processing

Consume queues, run Cron Triggers, orchestrate Workflows, process webhooks, and retry asynchronous work.

05

AI and vector workloads

Call Workers AI, Vectorize, AI Gateway, Browser Run, or external model providers.

06

Media and transformation

Coordinate Images, Stream, document conversion, HTML rewriting, and larger payload processing.

07

Multi-service architecture

Compose Workers with Service Bindings and isolate authentication, APIs, data, and frontend concerns.

08

Production software lifecycle

Use local tests, secrets, environments, versions, gradual deployment, logs, traces, and CI/CD.

5. Decision tree

1. Can a native Cloudflare Rule do it?
Yes: use Redirect, Transform, Cache, Configuration, Origin, or WAF Rules. No code is simpler to operate. No: continue.
2. Is it only lightweight request/response manipulation for rule-matched traffic?
Yes: continue toward a Snippet. No: use a Worker.
3. Does it fit inside 5 ms CPU, 2 MB memory, 32 KB package size, and the plan's 2–5 subrequests?
Yes: continue. No: use a Worker.
4. Does it need state, bindings, secrets, background triggers, application logs, or automated software releases?
Yes: use a Worker. No: use a Snippet.

6. Code comparison

Both use the Workers runtime, so simple code looks familiar. The difference is the surrounding platform and operating model.

Snippet: add a response header to rule-matched traffic

export default {
  async fetch(request) {
    const response = await fetch(request);
    const modified = new Response(response.body, response);
    modified.headers.set("x-edge-policy", "snippet");
    return modified;
  },
};

The associated Snippet rule decides exactly when this executes, for example only on a hostname and path prefix.

Worker: feature flag backed by KV

export default {
  async fetch(request, env) {
    const enabled = await env.FLAGS.get("new-checkout");

    if (enabled === "on") {
      return env.CHECKOUT_V2.fetch(request);
    }

    return env.CHECKOUT_V1.fetch(request);
  },
};

This requires bindings (FLAGS, CHECKOUT_V1, CHECKOUT_V2), persistent configuration, deployment configuration, and operational visibility — a Worker workload.

7. Deploy and operate

Snippet workflow
  1. Dashboard → zone → Rules → Snippets.
  2. Create from a template or enter JavaScript.
  3. Use HTTP Preview to test the request and output.
  4. Create the Snippet rule expression that selects traffic.
  5. Deploy directly or manage code + rule with Terraform/API.
Worker workflow
  1. Create a project with Wrangler or a framework.
  2. Define routes, custom domains, bindings, vars, and secrets.
  3. Develop locally and add unit/integration tests.
  4. Deploy a version, validate logs and metrics, then roll traffic.
  5. Operate with Workers Logs, traces, analytics, alerts, and CI/CD.
npm create cloudflare@latest -- workers-app
npx wrangler dev
npx wrangler deploy

8. When to migrate

Worker → Snippet

  • The Worker only changes headers, redirects, cache behavior, or origin routing.
  • It needs no bindings, storage, variables, secrets, or platform integrations.
  • The code and subrequests fit the Snippet limits.
  • Ruleset matching is a better control plane and eliminating usage billing matters.

Snippet → Worker

  • The Snippet approaches CPU, memory, package, or subrequest limits.
  • The logic now needs KV, D1, R2, Durable Objects, Queues, AI, or Service Bindings.
  • The workload needs unit tests, local development, environments, rich logs, or deployment automation.
  • The logic is becoming an application instead of a small traffic rule.
Because both products share the Workers runtime, straightforward JavaScript usually migrates cleanly. The work is mainly moving traffic matching, bindings, configuration, deployment, and observability to the destination product.

9. Gotchas and recommendations

  • Snippets are not available on Free zones. They are included at no additional cost on Pro, Business, and Enterprise.
  • Version Management does not currently support Snippets. Use Terraform/API and source control for repeatable change management.
  • Redirect hops consume subrequests. A Snippet fetch that follows one redirect uses two of the small subrequest allowance.
  • Order matters. Snippets inherit modifications from earlier Rules products; multiple Snippets run sequentially and later logic can change prior results.
  • Use proxied DNS. Snippets only apply when the domain or subdomain traffic passes through Cloudflare.
  • A shared runtime does not mean equal capabilities. Snippets intentionally exclude bindings, state, Cron Triggers, and Workers observability.
  • Avoid challenge loops. Test interactions between Snippet logic and challenge-producing security rules.
Default recommendation: Rules first, Snippets second, Workers third. Move upward only when the simpler layer cannot meet the functional or operational requirement.
