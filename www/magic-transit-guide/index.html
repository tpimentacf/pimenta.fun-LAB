Cloudflare Magic Transit

Network-layer (L3) DDoS protection and firewalling for entire IP prefixes. Cloudflare announces your prefixes from its anycast network, scrubs attack traffic at the edge, and delivers only clean packets to your data centers through tunnels.

0. What it is

Magic Transit protects IP networks, not individual hostnames. It works for any IP protocol — TCP, UDP, ICMP, GRE — so it covers game servers, VPN concentrators, mail, DNS, VoIP, and whole data centers, not just websites.

ADVERTISE

BGP anycast

Cloudflare announces your /24 (or larger) from every data center, so Internet traffic to your IPs lands on the nearest Cloudflare location.

PROTECT

Scrub at the edge

DDoS mitigation and Cloudflare Network Firewall (formerly Magic Firewall) rules run in every location before traffic moves on.

DELIVER

Tunnels to you

Clean packets travel over GRE, IPsec, or Cloudflare Network Interconnect (CNI) to your routers, selected by static routes or BGP.

Magic Transit vs CDN/WAF proxy: the CDN proxies HTTP(S) for a hostname and terminates TLS. Magic Transit forwards raw IP packets for a prefix. Your servers keep their own IPs, certificates, and TCP sessions.

Rules of thumb: lower priority wins; equal priority uses ECMP (weights tune the split); longest prefix always wins over priority; scope routes to regions near the data center to reduce last-hop latency.

6. Configuration steps

  1. Prepare IP space

    Own a publicly routable prefix of at least /24, or request Cloudflare-leased IPs. Create/update the IRR route object and RPKI ROA for the originating ASN, and draft the Letter of Agency (LOA).

  2. Onboard the prefix

    Cloudflare validates the LOA/IRR/ROA and creates the IP prefix plus a default BGP prefix. It stays withdrawn until you are ready.

  3. Verify router compatibility

    GRE or IPsec support, one tunnel per ISP, MSS clamping, and asymmetric flows for DSR.

  4. Create tunnels in Cloudflare

    curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/magic/gre_tunnels" \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{
    "name": "tun_dc1_ispA",
    "customer_gre_endpoint": "198.51.100.10",
    "cloudflare_gre_endpoint": "<CLOUDFLARE_ANYCAST_ENDPOINT>",
    "interface_address": "10.100.0.0/31",
    "mtu": 1476,
    "health_check": { "enabled": true, "type": "request", "direction": "unidirectional" }
  }'

  5. Configure the router side

    Example on Linux (mirror the same values on Cisco/Juniper/Fortinet/Palo Alto):

    ip tunnel add cf_ispA mode gre local 198.51.100.10 remote <CLOUDFLARE_ANYCAST_ENDPOINT> ttl 64
ip addr add 10.100.0.1/31 dev cf_ispA
ip link set cf_ispA mtu 1476 up

# clamp TCP MSS for traffic through the tunnel
iptables -t mangle -A FORWARD -o cf_ispA -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --set-mss 1436

# reply to Cloudflare health probes (allow ICMP from Cloudflare ranges)
iptables -A INPUT -i cf_ispA -p icmp -j ACCEPT

  6. Add routes

    curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/magic/routes" \
  --request POST \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{
    "prefix": "203.0.113.0/24",
    "nexthop": "10.100.0.1",
    "priority": 100,
    "weight": 128,
    "description": "DC1 via ISP A"
  }'

  7. Configure health checks

    Confirm tunnel health is healthy on the Network health page. Add endpoint health checks for critical IPs behind the tunnel. Use Request type with stateful firewalls.

  8. Configure Network Firewall and DDoS settings

    Start with allow rules for the services you expose (for example tcp/443 to 203.0.113.10, udp/51820 to the VPN), then a default block for the rest. Review DDoS managed ruleset sensitivity.

  9. Advertise the prefix

    curl "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/addressing/prefixes/$PREFIX_ID/bgp/prefixes/$BGP_PREFIX_ID" \
  --request PATCH \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{ "on_demand": { "advertised": true } }'

    Then ask your ISPs to stop announcing the same prefix (or announce it less-specific / prepended) so Cloudflare's path is preferred.

  10. Validate and monitor

    Check traceroutes land on Cloudflare, confirm traffic in Magic Transit analytics, and set notifications for tunnel health and DDoS events.

  • Tunnel flapping / unhealthy with stateful firewall: switch health check type from Reply to Request.
  • IPsec up but no traffic: disable anti-replay (or set window to 0); check crypto parameters.
  • Large transfers stall: MSS clamp missing or DF set.
  • Route not used: a more-specific route or lower priority value elsewhere is winning.

9. FAQ: can I advertise single IPs (for example two /32s)?

No. The Internet does not globally accept IPv4 announcements longer than /24, so Magic Transit only onboards and advertises prefixes of /24 or larger. Addresses such as 93.94.103.254 and 93.94.103.255 cannot be announced on their own.

  • If you control the whole /24 (for example 93.94.103.0/24): onboard and advertise the /24 with LOA, IRR, and ROA. Then use routes to send smaller subnets inside it to different tunnels. Cloudflare's traffic-steering docs show subnets such as /29, and longest-prefix match applies within the /24.
  • If you only have a few IPs: use Cloudflare-leased IPs for Magic Transit. No LOA is needed; egress is enabled automatically.
  • If you only need HTTP(S): the CDN/WAF proxy or Spectrum protects individual hostnames and ports without owning a /24.
Also note: .255 is the broadcast address of a /24 and is not normally assigned to a host.
