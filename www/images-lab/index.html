Cloudflare Images & Transformations

Cloudflare resizes, recompresses, and reformats images at the edge — no build pipeline, no origin work. This lab explains the two ways to do it (URL transformations and the Images product), then lets you build /cdn-cgi/image/… URLs live against a real sample and see the bytes shrink.

Checking whether image transformations are enabled on this zone…

Two ways to optimize images

Both deliver optimized bytes from Cloudflare’s edge; they differ in where the original lives and how you address it.

  • Image Transformations — transform images that already live on your origin (or any allowed URL). You address them through the /cdn-cgi/image/<options>/<source> path, or from a Worker via fetch(url, { cf: { image: … } }). No upload, no storage — Cloudflare pulls the source, transforms, and caches the result.
  • Cloudflare Images (product) — you upload and store originals with Cloudflare and serve them from imagedelivery.net using named variants. Includes direct-creator upload, signed URLs, and per-image analytics. Storage + delivery are billed together.

Anatomy of a transformation URL

A transformation is just a special path prefix in front of your image path.

/cdn-cgi/image/width=400,quality=75,format=auto/images-lab/sample.png
Prefix — fixed magic path handled by the edge.
Options — comma-separated key=value list.
Source — a path on this zone (or a full allowed URL).
The source can be a relative path on the same zone (as above) or a full URL. Full URLs from other origins only work when the zone setting is open; with on (this zone’s current mode) only same-zone paths are transformed.

Sizes are measured from the actual bytes the browser downloads (Content-Length). format=auto serves AVIF or WebP when your browser advertises support — often a fraction of the original.

The most useful transformation options. Combine any of them in the comma-separated list.

The Worker API (cf.image)

For full control — auth, allow-lists, dynamic sizing — transform from inside a Worker by passing a cf.image object to fetch().

// workers/img-resize/src/index.js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const src = url.searchParams.get("image");
    if (!src) return new Response("missing ?image=", { status: 400 });

    // Optional: only allow images from your own zone
    const allowed = "https://www.pimenta.fun/";
    if (!src.startsWith(allowed)) return new Response("forbidden", { status: 403 });

    return fetch(src, {
      cf: {
        image: {
          width: Number(url.searchParams.get("w")) || 800,
          quality: 80,
          format: "auto",
          fit: "cover"
        }
      }
    });
  }
}

The <img> markup for a page just points at the transform path — and you can generate a responsive srcset:

<img
  src="/cdn-cgi/image/width=800,format=auto/images-lab/sample.png"
  srcset="/cdn-cgi/image/width=480,format=auto/images-lab/sample.png 480w,
          /cdn-cgi/image/width=960,format=auto/images-lab/sample.png 960w"
  sizes="(max-width: 640px) 480px, 960px"
  width="800" height="533" alt="Sample" />

Transformation flows (no-code automation)

The URL and Worker methods above are explicit — you opt each image in. A flow is the opposite: a zone-level rule that transparently rewrites matching image requests through the Images service, so your existing URLs get optimized automatically with no /cdn-cgi/image/ prefix and no Worker. You configure them in the dashboard under Images → Transformations → Automation.

  • Custom flow — your own conditions (what to match) paired with actions (which optimizations to apply). Best for broad, consistent rules like “transcode everything to AVIF” or “force 100×100 under /thumbnail”.
  • Provider flow — a translation layer for migrating off another optimizer. Cloudflare currently supports Fastly Image Optimizer: your existing Fastly URLs (e.g. ?width, ?orient) keep working while Cloudflare maps them to its own parameters.

How a request is matched

  • Flows are evaluated top to bottom; the first matching flow runs and the rest are skipped (reorder in the dashboard to set priority).
  • If no flow matches, the request passes through to your origin unmodified.
  • Custom flows only trigger on supported image extensions — HTML, CSS and other non-images are never touched.
  • Flows run after HTTP redirect rules, and include loop prevention (a request already coming from the Images service won’t re-trigger the flow).
  • Transformations must be on for the zone first — this zone already is (see Enable & verify).

Custom flow: conditions

A flow fires only when all configured conditions match.

ConditionExampleMatches when…
File extensionjpeg, png, webpthe request is for one of the chosen image formats (or all formats).
URL path/images-lab/*the path matches the pattern, e.g. everything under a directory.
Query parameterorientthe query string contains the named parameter.

Example — auto-optimize this lab’s images

A single custom flow that transcodes and responsively sizes every image under /images-lab/:

# Images → Transformations → Automation → Add custom flow
# Flow name: "Optimize lab images"

WHEN  (all conditions match)
  file extension   is   jpeg, png, webp
  URL path         is   /images-lab/*

THEN  (apply these actions)
  format   = auto     # AVIF/WebP negotiated per browser
  quality  = 80       # or a perceptual level: high / medium-high / ...
  width    = auto     # size to the requesting device via client hints

With that flow live, this plain markup is optimized automatically — note there is no transform prefix in the src:

<img src="/images-lab/sample.png" alt="Cloudflare Lisbon office" />

Cloudflare rewrites that request through Images on the edge and serves an AVIF/WebP, device-sized version — while the original URL, your HTML, and your origin file all stay exactly the same.

Flows produce transformations under the hood, so they are billed the same way (per unique transformation, with caching). Because a broad path rule can match a lot of traffic, scope conditions tightly and watch usage.

The Cloudflare Images product

When you want Cloudflare to store the originals too, not just transform origin images.

  • Upload via API, dashboard, or direct creator upload (one-time upload URL handed to an end user so files never touch your server).
  • Variants — named, reusable transform presets (e.g. thumbnail, hero). Delivery URLs look like https://imagedelivery.net/<hash>/<image-id>/<variant>.
  • Signed URLs — require a token + expiry for private images.
  • Flexible variants — opt in to allow ad-hoc transform parameters on delivery URLs instead of only pre-defined variants.
# Upload an image with the Images API
curl -X POST \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/images/v1" \
  -H "Authorization: Bearer $CF_IMAGES_TOKEN" \
  -F "file=@sample.png"

Enable & verify

URL transformations must be turned on per zone before /cdn-cgi/image/ works. This zone is already set to on.

  • Dashboard — the zone → Images → Transformations → enable “Transform via URL”. Choose whether to allow other origins.
  • API — set the image_resizing zone setting to on (same-zone only) or open (any origin URL):
curl -X PATCH \
  "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/settings/image_resizing" \
  -H "X-Auth-Email: $CF_EMAIL" -H "X-Auth-Key: $CF_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"value":"on"}'

# Verify a transform returns an image (HTTP 200, content-type image/*)
curl -sI "https://www.pimenta.fun/cdn-cgi/image/width=64/images-lab/sample.png" | grep -i "content-type"
Transformations are a billed feature (priced per unique transformation, with caching). Leave it on rather than open unless you specifically need to transform third-party origins.
