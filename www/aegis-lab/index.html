Cloudflare Aegis — Dedicated CDN Egress IPs

By default, Cloudflare reaches your origin from a huge pool of egress IPs shared by every customer, so your origin firewall has to trust all of them. Aegis — now called Dedicated CDN Egress IPs — gives your account a small set of reserved egress IPs, so you can lock the origin down to accept traffic from only those addresses.

Enterprise feature. Configured through the aegis zone setting (contact your account team for an egress pool ID). This page is a build/architecture guide — it does not enable anything on this zone.

What Aegis is Enterprise

Reserved egress IP addresses for origin allowlisting and increased security.

When Cloudflare acts as a reverse proxy, its global network sits between clients and your origin. The connection Cloudflare opens to your origin normally comes from a very large, publicly documented pool of IPs used by all Cloudflare customers. That means your origin firewall must allow that entire range — and anyone else behind Cloudflare could, in principle, reach an origin that only checks “is this a Cloudflare IP?”.

Dedicated CDN Egress IPs (formerly Aegis) reserve a set of egress IPs exclusively for your account. You then allowlist just those addresses on your origin, so only your Cloudflare traffic can connect. It works for layer 7 WAF/CDN services and for Spectrum, and pools can be assigned across single or multiple zones and even across accounts.

Ingress vs egress

Two halves of every proxied request. Aegis changes the egress half.

The core idea: shared vs dedicated egress

Same request path — the difference is which source IPs your origin has to trust.

How a request flows through Cloudflare

End to end, and where the dedicated egress IP is applied.

  1. Ingress — the client connects to the nearest Cloudflare data center by Anycast routing; TLS terminates and the request is inspected.
  2. Edge processing — WAF, rules, Workers, and cache lookup run. A cache hit is served here and never touches your origin.
  3. Egress decision — on a cache miss, the cache service asks an egress router to connect to the origin. With Aegis, an egress IP reserved for your account is used.
  4. Origin allowlist — your firewall sees a source IP from your dedicated pool and permits it; everything else is dropped.
  5. Response — the origin replies back through Cloudflare to the client (and may be cached for next time).

Connection forwarding (IPv4)

A dedicated IPv4 lives in a few chosen locations near your origin — not in every data center. When the ingress server has no applicable IP, Cloudflare forwards the connection to one that does.

  • IPv6 ranges are deployed globally, so no forwarding is needed — any data center can egress with your dedicated IPv6.
  • IPv4 addresses are placed in locations you choose with your account team (ideally near your origin); each IPv4 can be split across up to four locations. IPs do not forward in response to traffic spikes — capacity per location is provisioned instead.
  • Each dedicated egress IP supports 40,000 concurrent connections per origin IP:port, and benefits from connection reuse and coalescing.
  • Not available in the Cloudflare China Network. If you use Regional Services, provision dedicated IPs in those same regions.

Worked example: egress pinned to the Madrid POP

Suppose your dedicated Aegis IPv4 (203.0.113.10) is provisioned in one location — the Madrid POP, near your origin. Users still land on their nearest Cloudflare POP (Anycast ingress), but every origin connection egresses from Madrid.

  1. Anycast ingress — the Lisbon, London, New York, and Frankfurt users each connect to their nearest Cloudflare POP. Latency to the edge stays low worldwide.
  2. No local dedicated IP — those POPs don’t hold your Aegis IPv4, so on a cache miss the egress connection is forwarded to the closest POP that does — Madrid.
  3. Single egress source — Madrid opens the origin connection from 203.0.113.10, regardless of where the user came from.
  4. Origin allowlist — your firewall permits only 203.0.113.10/32; all other sources are dropped. One rule covers every user, everywhere.

Trade-off: pinning egress to Madrid adds a POP-to-POP hop for far-away users (e.g. New York), so place dedicated IPv4s near your origin and, for global low-latency egress, consider dedicated IPv6 (deployed globally, no forwarding) or provisioning IPv4 in up to four locations.

One egress POP vs two egress POPs

Adding a second dedicated location (Lisbon alongside Madrid) shortens the egress path for nearby users, splits capacity, and adds redundancy — at the cost of one more IP to allowlist on the origin.

AspectOne egress POP (Madrid)Two egress POPs (Madrid + Lisbon)
Egress pathAll users hop to Madrid, even far ones. Each user egresses from the nearer POP — shorter path, lower latency.
Origin allowlistOne IP: 203.0.113.10/32. Two IPs: .10/32 and .20/32.
Capacity40k conns per origin IP:port on one IP. Split across two IPs / locations — more headroom.
ResilienceMadrid is a single point for egress. If one location is impaired, forwarding falls back to the other.
Cost / setupSimplest — one location to provision. More IPs/locations to provision and allowlist.

A single IPv4 can be split across up to four locations; work with your account team to place them near where your users (and origin) are. For global egress with no forwarding at all, dedicated IPv6 is deployed across every data center.

Benefits

  • Origin lockdown — allow traffic from only your small list of dedicated IPs, dramatically shrinking the trust surface versus allowing all shared Cloudflare ranges.
  • Access & CNI — combine with Cloudflare Access and Cloudflare Network Interconnect to secure apps without installing software or changing origin code. Dedicated egress IPs can be advertised over CNI via BGP.
  • Authorized Workers only — ensure only your authorized Workers can reach your origin services.
  • Flexible scope — assign a pool to one zone, many zones, or across accounts.

Implement it

Aegis is enabled per zone through the aegis zone setting, using an egress pool ID your account team provides.

Allowlist first. Add the dedicated IPs to your origin firewall before linking the pool to a zone. If you enable it first, traffic will egress from IPs your origin rejects — causing errors.

Requirements

  • Enterprise plan; contact your account team to request access and get the pool ID.
  • The account must own leased IPs or have a delegated BYOIP prefix.
  • A pool is either BYOIP or leased IPs — never mixed. A single BYOIP prefix is used for CDN ingress or egress, not both.

1. Turn on Aegis for a zone

# PATCH the "aegis" zone setting with your egress pool ID
curl "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/settings/aegis" \
  --request PATCH \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{
    "id": "aegis",
    "value": { "enabled": true, "pool_id": "<EGRESS_POOL_ID>" }
  }'

Requires the Zone Settings Write token permission.

2. Check status

curl "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/settings/aegis" \
  --request GET \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN"

3. Turn it off

curl "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/settings/aegis" \
  --request PATCH \
  --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  --json '{ "id": "aegis", "value": { "enabled": false } }'

Find leased dedicated egress IPs in the dashboard under Address space → Leased IPs; for BYOIP, see BYOIP prefixes. Track usage via the GraphQL Analytics API.
