Cloudflare Precursor

Most bot defenses judge a single request. Precursor judges the whole session: a client-side script runs continuously in the browser, streams behavioral and environmental signals to Cloudflare, and updates the visitor’s trust state in the cf_clearance cookie over time — catching automation that looks fine request-by-request but is non-human across a session.

What Precursor is

Client-side, session-based verification that continuously evaluates visitor behavior to identify automation.

A one-time challenge is a snapshot: a bot that solves it once (or replays a stolen cf_clearance cookie) is trusted until the cookie expires. Precursor turns verification into a continuous loop that keeps watching after the visitor is let in:

  • A client-side script is injected into the page by Cloudflare.
  • The script continuously collects signals (environment + behavior) and performs verification.
  • Each execution produces signals that are evaluated by Cloudflare at the edge.
  • Results update session state stored in the cf_clearance cookie.
  • The process repeats throughout the session — so trust can go down, not just up.

The result: clearance becomes both time-bound (the interstitial challenge that first set it) and behavior-bound (Precursor, which can reduce or invalidate it mid-session).

Clearance & challenge state

cf_clearance is an HttpOnly cookie, so page JavaScript can never read it via document.cookie. Detection here happens on the actual page request: the precursor-clearance Worker on this route reads the request Cookie header the edge received and reports the result via window.__cfClearance (first load) and an X-CF-Clearance response header (each re-fetch). No separate/external request is made.

Enable & implement

Precursor is a zone-level toggle — no code, no origin changes. Enabling it is the whole “implementation” for most sites.

  1. In the Cloudflare dashboard, select your zone.
  2. Go to Security → Settings.
  3. Locate Precursor and turn it on.
  4. Choose a mode — Minimize Friction (default) or Maximize Security (recommended). For most customers this is the only required configuration.
  5. Disable JavaScript Detections (JSD) — Precursor supersedes it (see How it fits).
Precursor runs across the whole zone once enabled. Verify in Security → Analytics → Traffic → Bot analysis that its detections appear before you build enforcement rules on top of it.

Modes

A fully verified session may require a lightweight challenge to establish valid state. The mode decides whether that challenge is ever shown.

ModeInterstitial?Trade-off
Minimize Friction
default		 No. Establishes session state in the background. Smoothest UX, but cannot guarantee every session is fully verified.
Maximize Security
recommended		 Yes — a lightweight challenge if no valid session exists yet. Every session is verified before proceeding; may add a little friction.

Precursor rules (optional)

Precursor runs everywhere by default. Rules do not turn it on or off — they choose which mode applies per request. Common patterns:

  • Run Minimize Friction across the site, but enforce Maximize Security on /checkout and /login.
  • Run Maximize Security everywhere except the homepage.
# Security → Settings → Precursor → Rules (conceptual)
# Sensitive flows: strict verification
WHEN  http.request.uri.path in {"/checkout" "/login"}
THEN  mode = Maximize Security

# Everything else: keep it smooth
DEFAULT
THEN  mode = Minimize Friction

Rules are evaluated with the same request fields you already use in WAF custom rules, so you can scope by path, host, country, ASN, and so on.

How Precursor fits with the rest of the stack

vs. JavaScript Detections (JSD) — it replaces it

  • JSD runs once per HTML request and sets a pass/fail flag (cf.bot_management.js_detection.passed).
  • Precursor moves to continuous verification, adds session state, and enables dynamic runtime control. If you enable Precursor, disable JSD.

vs. Challenge Pages — it strengthens them

  • Challenges are point-in-time; Precursor is continuous. It does not replace challenges.
  • It decides when extra challenges are needed, re-evaluates visitors after they already passed one, and spots automation that only emerges over time.

The cf_clearance cookie

  • Precursor is tightly integrated with clearance. During a session it can reduce or invalidate effective clearance, trigger additional challenges, or re-verify the visitor — even if the cookie has not expired.

Security Analytics

  • Once Precursor runs, its behavioral / biometric detections feed the zone’s bot score distribution and WAF rule-match counts under Security → Analytics → Traffic → Bot analysis.

Labs — test Precursor on this zone

Concrete experiments to confirm Precursor is working and to see its effect. Run them against a page on a zone where Precursor is enabled.

#ExperimentWhat to observe
1Load a page in a real browser, then open DevTools → Application → Cookies. A cf_clearance cookie is present. In DevTools → Network, a /cdn-cgi/challenge-platform/… script is fetched.
2Stay on the page and interact for a minute, watching the cookie value. Clearance is re-evaluated over the session — the value can change as new signals are scored (behavior-bound clearance).
3Set a Precursor rule: Maximize Security on /checkout. Hitting that path with no valid session shows a lightweight interstitial; other paths (Minimize Friction) do not.
4Compare a real browser vs. a headless one (Playwright / Puppeteer) hitting the same page. navigator.webdriver=true, missing behavior, and uniform timing push the session toward a low bot score / re-challenge.
5curl the page (no JS engine) and inspect headers. No clearance is established; behind Maximize Security the request is challenged/blocked rather than served.
6Open Security → Analytics → Bot analysis. Precursor detections appear in the bot score distribution and rule-match counts.
7Add a WAF custom rule acting on the bot score for a sensitive path. Precursor-informed sessions are challenged/blocked; legitimate sessions pass.

curl vs. browser (lab 5)

# A scripted client has no JS runtime, so it never runs the Precursor loop.
# Under Maximize Security it should be challenged instead of served the page.
curl -sS -o /dev/null -w "%{http_code}\n" https://www.pimenta.fun/precursor-lab/

# Show the mitigation / ray headers Cloudflare returns:
curl -sI https://www.pimenta.fun/precursor-lab/ | grep -Ei "cf-ray|cf-mitigated|server"

WAF custom rule on the resulting score (lab 7)

# Example expression: challenge low-scoring sessions on a sensitive path.
(http.request.uri.path eq "/checkout") and (cf.bot_management.score lt 30)
    # action: Managed Challenge

Because Precursor feeds the bot score, rules like this become session-aware: a client that passed an initial challenge but then behaves like automation can still be caught.
