AI & Agents

Making a site Agent-Ready

The web is being read and acted on by autonomous agents, not just humans in browsers. An agent-ready site is discoverable, machine-readable, actionable, and transactable by an LLM agent — from robots.txt and Markdown negotiation all the way to MCP, OAuth, Agent Skills, and agentic commerce.

This is a roadmap, not a single feature. Each pillar below is independently useful — start at the top (cheap, static wins) and work down toward tools, auth, and payments. Everything maps to Cloudflare where relevant.

1 · Discoverability & crawl policy

Agents (and the crawlers that feed them) look for a handful of well-known files first. Ship them.

robots.txt with explicit AI directives

Generic User-agent: * rules are ignored by many AI crawlers that match their own token. Name them. Allow the bots you want indexing you; block the ones you don’t.

# /robots.txt
User-agent: *
Allow: /

# AI search / assistants you WANT to be cited by
User-agent: OAI-SearchBot
Allow: /
User-agent: PerplexityBot
Allow: /

# Training crawlers you may want to limit
User-agent: GPTBot
Disallow: /private/
User-agent: ClaudeBot
Disallow: /private/
User-agent: Google-Extended
Disallow: /private/
User-agent: CCBot
Disallow: /

Sitemap: https://www.pimenta.fun/sitemap.xml
Cloudflare shortcut: AI Crawl Control (dashboard) manages a hosted robots.txt and lets you allow/block individual AI bots per zone, and Pay Per Crawl lets you charge crawlers with HTTP 402 for access — no code required.

llms.txt — a README for LLMs

A single Markdown file at /llms.txt that curates your most important pages, so an agent doesn’t have to crawl and guess. Optionally add /llms-full.txt with the full text inlined.

# /llms.txt

sitemap.xml

Still the canonical machine index of URLs. Reference it from robots.txt. Keep <lastmod> honest so agents can prioritise fresh content.

2 · Markdown content negotiation

Your HTML is built for humans — nav, CSS, scripts. Agents want the content. Serve a clean Markdown rendition when they ask for it, and token cost drops while parsing accuracy jumps.

Three ways an agent signals "give me Markdown"
  • Accept header: Accept: text/markdown — the cleanest, content-negotiation-native way.
  • Query flag: ?format=md — trivial to add and easy to link.
  • Suffix: /page.md — a parallel URL that returns Markdown.

A Worker in front of your pages can do this with zero origin changes — the same edge-injection pattern as the Turnstile injection Worker:

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    const accept = request.headers.get("accept") || "";
    const wantsMd = accept.includes("text/markdown")
      || url.searchParams.get("format") === "md"
      || url.pathname.endsWith(".md");

    const res = await fetch(request);         // origin HTML
    if (!wantsMd) return res;

    const html = await res.text();
    const md = htmlToMarkdown(html);       // strip chrome, keep content
    return new Response(md, {
      headers: { "content-type": "text/markdown; charset=utf-8",
                 "vary": "accept" }   // so caches keep both variants
    });
  }
};
Don’t forget Vary: Accept so Cloudflare’s cache stores the HTML and Markdown variants separately instead of serving one to everyone.

3 · Machine-readable semantics

Even in HTML, structured data makes entities unambiguous: what is a product, a price, an author, an action. Agents (and AI search) lean on it heavily.

  • JSON-LD (schema.org): the highest-leverage add — Product, Offer, Article, Organization, FAQPage.
  • Open Graph / meta: title, description, canonical URL, lang.
  • Semantic HTML: real <article>, <nav>, <main>, headings in order.
<!-- Inline JSON-LD an agent can read straight off the page -->
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Product",
  "name": "Lab T-Shirt",
  "offers": {
    "@type": "Offer",
    "price": "25.00",
    "priceCurrency": "USD",
    "availability": "https://schema.org/InStock"
  }
}
</script>

4 · MCP — give agents tools, not just text

Reading is passive. The Model Context Protocol (MCP) lets an agent do things on your site by calling typed tools and reading resources — the USB-C port for AI.

You already run one: workers/ai-mcp exposes notes CRUD, KV get/put, and an ask_ai tool, and the AI Chat Agent consumes it. To be agent-ready, make it discoverable and documented.
  • Transport: Streamable HTTP (the current standard; SSE-only is deprecated) so any remote agent can connect.
  • Typed tools: clear names, JSON-Schema inputs, and human-readable descriptions — the description is the prompt.
  • Discovery: publish the endpoint in llms.txt and a .well-known manifest; list it in registries.
  • Cloudflare: build with the agents SDK (McpAgent) / workers-mcp; deploy remote MCP on Workers.
// Registering a typed tool (Cloudflare agents SDK)
server.tool(
  "get_order_status",
  "Look up the status of an order by its ID.",
  { orderId: z.string().describe("The order ID, e.g. ORD-1234") },
  async ({ orderId }) => ({
    content: [{ type: "text", text: await lookup(orderId) }]
  })
);

5 · OAuth — let agents act as the user, safely

Anonymous tools are fine for public data. The moment an agent acts on a user’s behalf (their orders, their notes, their money) it needs delegated, scoped, revocable auth. MCP standardises on OAuth 2.1.

PieceWhat it does
OAuth 2.1 + PKCEAuthorization-code flow with PKCE is mandatory — the agent never holds your password, only a scoped token.
/.well-known/oauth-protected-resourceRFC 9728 metadata telling the agent which authorization server guards this MCP resource.
/.well-known/oauth-authorization-serverRFC 8414 metadata: authorize/token endpoints, supported scopes and methods.
Dynamic Client RegistrationRFC 7591 — lets an unknown agent register itself, so you don’t pre-provision every client.
ScopesLeast privilege: notes:read, orders:write… short-lived tokens, easy revocation.
Cloudflare shortcut: @cloudflare/workers-oauth-provider turns a Worker into a spec-compliant OAuth 2.1 server and wraps your MCP handler, emitting the .well-known documents for you.
# /.well-known/oauth-protected-resource
{
  "resource": "https://mcp.pimenta.fun",
  "authorization_servers": ["https://mcp.pimenta.fun"],
  "scopes_supported": ["notes:read", "notes:write"],
  "bearer_methods_supported": ["header"]
}

6 · Agent Skills — teach agents how to use you

A Skill is a folder of instructions (and optional scripts) an agent loads on demand to learn a workflow — “how to place an order on pimenta.fun”, “how to query the lab notes MCP”. It’s progressive disclosure: the agent reads the name/description first, then the body only when relevant.

# skills/shop-on-pimenta/SKILL.md
---
name: shop-on-pimenta
description: Browse the pimenta.fun catalogue and place an order via the
  storefront API. Use when the user wants to buy lab merch.
---

# Shopping on pimenta.fun

1. Fetch the product feed: `GET /feed/products.json`
2. Confirm item + quantity with the user.
3. Create a checkout: `POST /api/checkout` with the line items.
4. Return the payment link or confirmation to the user.

See `reference.md` for the full API and error codes.
  • Portable: the same SKILL.md works across agent runtimes that support the format.
  • Composable: bundle scripts/templates the agent can run, not just prose.
  • Publishable: host the folder so agents (and this lab) can download and load it.

7 · Agentic commerce — let agents transact

The end game: an agent completes a purchase for a user. That needs a machine-readable catalogue, an agent-callable checkout, and a delegated payment mandate so the agent pays without ever touching raw card data.

ProtocolBacked byGist
ACPOpenAI + StripeAgentic Commerce Protocol — product feed + checkout API + shared payment token; powers ChatGPT “Instant Checkout”.
AP2GoogleAgent Payments Protocol — cryptographically signed “mandates” that prove user intent to pay.
Intelligent CommerceVisaTokenised, agent-scoped payment credentials with spend controls.
Agent PayMastercardAgent-initiated payments with tokenised card mandates.
The three building blocks, regardless of protocol
// 1. Machine-readable catalogue  ->  GET /feed/products.json
{ "products": [
  { "id": "tshirt", "title": "Lab T-Shirt",
    "price": "25.00", "currency": "USD", "in_stock": true }
] }

// 2. Agent-callable checkout  ->  POST /api/checkout
{ "items": [{ "id": "tshirt", "qty": 1 }],
  "buyer": { "email": "user@example.com" } }
// -> { "checkout_id": "...", "total": "25.00", "pay_url": "..." }

// 3. Delegated payment: agent presents a signed mandate / shared
//    payment token, never the user's raw card.
Security moves to the front. Agent checkout means bots with valid-looking sessions. Pair it with Turnstile/verification on sensitive actions, per-agent rate limits, spend caps in the mandate, and the leaked-credential / bot controls covered in the e-commerce security lab.

Cross-cutting · Verified agents (Web Bot Auth)

“Agent-ready” doesn’t mean “let every bot in.” The problem is telling a legitimate agent from an abusive one. Web Bot Auth (a Cloudflare-driven effort) has agents cryptographically sign their requests with HTTP Message Signatures (RFC 9421) against a published key directory — so you can allow verified agents and challenge the rest.

  • Identify, don’t just block: signed requests prove which agent is calling.
  • Policy per agent: allow verified assistants to your MCP/checkout, rate-limit or challenge unknowns.
  • Cloudflare: AI Crawl Control + verified-bot signals + Turnstile give you the enforcement layer.

Implementation — step by step

A phased rollout ordered cheapest → richest. Each phase says what to add, where, why we do it, and how to verify. On this lab, static files live in www/ (served by Apache), and Workers live in workers/<name>/ bound to a www.pimenta.fun/<path>* route.

Phase 0 · No code

Set crawl & bot policy in the Cloudflare dashboard

Why: agent traffic is bot traffic. Before you invite agents in, decide who is allowed and how you’ll tell good agents from abusive ones — otherwise “agent-ready” just means “easier to scrape and abuse.”

  1. AI Crawl Control → set a per-AI-bot allow/block policy and a hosted robots.txt baseline.
  2. Bots → Verified Bots / Web Bot Auth → note which agents are cryptographically verifiable; decide allow vs. challenge.
  3. (Optional) Pay Per Crawl → charge crawlers with HTTP 402 if you want to monetise access.
  4. Confirm AI Gateway fronts Workers AI (the ai-mcp ask_ai tool already routes through it).

Verify: policies show active in the dashboard; blocked bots receive a challenge/403.

Phase 1 · Static files

Ship the discoverability files agents look for first

Why: agents and their crawlers probe a few well-known URLs before anything else. These three files are the cheapest, highest-leverage step — they let an agent find your content and know what it may use, with zero runtime cost.

  1. Add www/robots.txt — per-bot User-agent/Allow/Disallow blocks plus a Sitemap: line.
  2. Add www/sitemap.xml — one entry per www/**/index.html with an honest <lastmod> so agents prioritise fresh pages.
  3. Add www/llms.txt — a curated Markdown index (derive it from the docs catalogue). Optionally add llms-full.txt with text inlined.

Verify: curl https://www.pimenta.fun/robots.txt (and /sitemap.xml, /llms.txt) return 200 with the right content-type.

Phase 2 · Worker

Serve Markdown on content negotiation

Why: your HTML is styled for humans; agents pay (in tokens) to strip the chrome. Returning clean Markdown when asked cuts their cost and raises parsing accuracy — and a Worker does it with no origin changes.

  1. Create workers/markdown-negotiation/ (worker.js + wrangler.toml + README.md).
  2. Logic: if Accept: text/markdown, ?format=md, or a .md suffix → fetch origin HTML, convert, return text/markdown with Vary: Accept; otherwise pass through untouched.
  3. Route it narrowly first (e.g. www.pimenta.fun/docs*), then widen once verified.

Verify: curl -H "Accept: text/markdown" https://www.pimenta.fun/docs/ returns Markdown; a normal browser still gets HTML.

Phase 3 · Markup

Add structured data (JSON-LD) to key pages

Why: even when an agent reads HTML, JSON-LD removes ambiguity — it states outright what is a product, a price, an author, an action. It’s also what AI search engines lean on to cite you.

  1. Add <script type="application/ld+json"> blocks: Organization on the home page.
  2. Product/Offer on the e-commerce and any shop pages.
  3. TechArticle on the guide pages.

Verify: a schema.org / Rich Results validator parses each page with no errors.

Phase 4 · MCP

Make the MCP server discoverable & documented

Why: reading is passive — MCP is how an agent acts. You already run workers/ai-mcp; being agent-ready means any remote agent can find it, understand its tools, and connect over the current transport.

  1. Deploy ai-mcp on a stable public host/route (e.g. mcp.pimenta.fun or www.pimenta.fun/mcp*).
  2. Use Streamable HTTP transport; give every tool a clear name, JSON-Schema inputs, and a human-readable description (the description is the prompt).
  3. Publish a .well-known manifest and list the endpoint in llms.txt.

Verify: connect from the Cloudflare AI Playground or an MCP client; tools/list returns your tools and one call succeeds.

Phase 5 · Auth

Add OAuth 2.1 so agents can act as the user

Why: the moment a tool touches a user’s private data or money, anonymous access is unacceptable. OAuth lets an agent act on the user’s behalf with a scoped, short-lived, revocable token — never the password.

  1. Wrap ai-mcp with @cloudflare/workers-oauth-provider.
  2. Serve /.well-known/oauth-protected-resource (RFC 9728) and /.well-known/oauth-authorization-server (RFC 8414); enable PKCE and Dynamic Client Registration.
  3. Define least-privilege scopes (notes:read, notes:write…) and keep tokens short-lived.

Verify: an MCP client triggers the OAuth flow and then calls a protected tool with a scoped token.

Phase 6 · Skills

Publish Agent Skills

Why: tools tell an agent what it can call; a Skill teaches it how to accomplish a goal on your site — the multi-step workflow, the order of calls, the error handling — loaded on demand so it doesn’t bloat every prompt.

  1. Add skills/query-lab-notes/SKILL.md (name + description frontmatter, then the workflow) for the MCP.
  2. Add skills/shop-on-pimenta/SKILL.md (+ optional reference.md) once the commerce API exists.
  3. Publish the folder in the repo and link it from the guide and llms.txt.

Verify: load the skill in a supporting agent runtime; it follows the documented steps end-to-end.

Phase 7 · Commerce

Expose an agent-callable catalogue + checkout

Why: the end game is an agent completing a purchase for a user. That needs a machine catalogue, a checkout an agent can call, and a way to pay without ever handling raw card data.

  1. Create workers/agent-commerce/: GET /feed/products.json (catalogue) and POST /api/checkout (line items → checkout + pay link).
  2. Adopt a payment rail (ACP with Stripe, or AP2-style signed mandates); the agent presents a token/mandate, never a card number.
  3. Cross-link it from the e-commerce security lab.

Verify: an agent fetches the feed, creates a checkout, and receives a pay_url / confirmation.

Phase 8 · Enforcement

Protect the agent surface

Why: opening tools and checkout to agents widens the attack surface — bots with valid-looking sessions. You want verified agents through and everything else challenged or throttled.

  1. Use Web Bot Auth / verified-bot rules: allow verified agents to /mcp and /api/checkout, challenge unknowns.
  2. Add Rate Limiting per agent on the MCP and checkout paths.
  3. Put Turnstile on sensitive actions (reuse the injection / login Workers) and set spend caps in the payment mandate.

Verify: unknown / high-volume agents get challenged or limited; verified agents pass through.

Suggested execution order: Phases 1–3 first (all in www/ plus one Worker, immediately verifiable), then 4–5 (MCP + auth), then 6–7 (Skills + commerce), and 8 (enforcement) alongside 7.

Implementation checklist

Roughly ordered from cheapest/static to richest/transactional.

  • robots.txt with per-AI-bot rules + Sitemap: line
  • sitemap.xml with honest lastmod
  • llms.txt (and optionally llms-full.txt) curating key pages
  • Markdown negotiation on Accept: text/markdown / ?format=md, with Vary: Accept
  • JSON-LD structured data on content and product pages
  • MCP server on Streamable HTTP with typed tools + a .well-known manifest
  • OAuth 2.1 for user-scoped tools, with the two .well-known metadata docs
  • Agent Skill(s) published as SKILL.md folders
  • Agentic commerce: product feed + checkout API + delegated payment mandate
