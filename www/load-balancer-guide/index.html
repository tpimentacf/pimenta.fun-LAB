Cloudflare Load Balancing

Distribute traffic across multiple origins for higher availability and lower latency. Cloudflare health-checks your servers, steers each visitor to the best pool, and fails over automatically when an origin goes down — all at the edge, before traffic reaches your infrastructure.

1. Anatomy

A load balancer is built from four objects. Understanding how they nest is the key to configuring everything else.

HOSTNAME

Load Balancer

A proxied hostname (e.g. app.example.com) that owns the steering policy, session affinity and the list of pools.

GROUP

Pool

A group of origins in one region/provider, with a health monitor and per-origin weights. Marked healthy/unhealthy as a unit.

SERVER

Origin

A single backend (IP or hostname) with an optional weight and its own health state.

PROBE

Monitor

The recurring health check (HTTP/TCP/…) that decides whether each origin — and therefore the pool — is up.

2. Steering methods

The steering policy decides which pool serves a request. Within the chosen pool, origins are then picked by their weights / load metric.

MethodHow a pool is chosenUse it for
Off (failover)Pools are used strictly in the order you list them; move to the next only when the current one is unhealthy.Simple active/passive DR.
RandomA healthy pool is chosen at random (weighted if you set pool weights).Even spread, no geo needs.
DynamicRoutes to the pool with the lowest round-trip time measured by monitors from each region.Latency-optimised, hands-off.
ProximityRoutes to the geographically closest origin using its configured latitude/longitude.Physical-distance routing.
GeoYou map regions/countries to specific pools; visitors in a region get that pool.Data residency, per-region backends (this lab's EU/US demo).
Least Outstanding RequestsWeights adjust to favour pools/origins with the fewest in-flight requests.Uneven request cost.
Least ConnectionsRoutes to the pool/origin with the fewest open connections.Long-lived connections.

3. Session affinity

By default each request is steered independently. Session affinity ("sticky sessions") pins a visitor to the same origin so stateful apps keep working.

  • By Cloudflare cookie — the edge sets a __cflb cookie holding the chosen origin; configurable TTL.
  • By IP address — hashes the client IP to an origin (no cookie needed; weaker behind shared NATs).
  • By header — sticks based on a request header value (Enterprise).
  • Drain / zero-downtime — on failure you can send affine traffic to another origin instead of dropping it.

4. Health & failover

Monitors probe each origin on a schedule. Consecutive failures mark an origin (and, once all are down, the pool) unhealthy; traffic then fails over to the next pool per the steering policy. Recovery is automatic once probes pass again.

Monitor settingMeaning
TypeHTTP, HTTPS, TCP, UDP-ICMP, ICMP-ping or SMTP.
Path & HostFor HTTP(S): the URL path probed and the Host/headers sent.
Expected codes / bodye.g. 2xx and an optional response-body substring.
IntervalHow often to probe (lower = faster detection, more load).
Timeout & RetriesPer-probe timeout and how many tries before failing.
Consecutive up/downHow many results flip the health state (debounces flapping).
RegionsWhich Cloudflare regions run the probe (also feeds Dynamic steering RTT).

5. Custom rules (header / geo overrides)

Load Balancing custom rules let you override pool selection with the full Rules expression language — by header, cookie, country, query string, and more. This is how you do header-based steering in addition to geo:

# Force the EU pool when a routing header is present
if  http.request.headers["x-region"][0] == "eu"
then use pool: eu-west-pool  (and disable session affinity, optional)

# Send a country to a specific pool
if  ip.geoip.country == "DE"
then use pool: eu-west-pool
Order matters Custom rules evaluate top-down; the first match wins and can either fix the pool or fall through to the default steering policy.

6. Configure it

  1. Create a health monitor

    Traffic → Load Balancing → Monitors. Pick HTTP(S), set the path (e.g. /health), expected code 200, interval and retries.

  2. Create the pools

    Create an EU-West pool and a US-East pool. Add each origin (IP/hostname + weight), attach the monitor, and set a notification email. A pool is healthy while it has at least one healthy origin.

  3. Create the load balancer

    Traffic → Load Balancing → Create. Choose the hostname, attach both pools, pick a steering method (Geo for the EU/US demo), and set the fallback pool.

  4. Map regions (geo steering) or add rules

    For Geo steering, map Western/Eastern Europe → EU pool and North America → US pool. Or add custom rules for header/country overrides.

  5. Set session affinity (if stateful)

    Enable cookie/IP affinity and a TTL so a visitor sticks to one origin.

  6. Test steering & failover

    curl -sI https://app.example.com                 # see which pool served you
curl -sI https://app.example.com -H "x-region: eu"  # header override
# then stop the EU origin and watch traffic move to US

8. Notes & gotchas

  • Load Balancing is a paid add-on billed by DNS queries; health checks from many regions add cost — tune the interval.
  • A fallback pool is required — it receives traffic when every other pool is unhealthy (better a slow origin than an error).
  • Geo steering resolves the visitor region at the edge; behind a VPN/WARP the region may differ from the user's physical location.
  • Proxied (orange-cloud) hostname is required for HTTP-aware steering, affinity and rules; grey-cloud LBs are DNS-only.
  • Monitors must be able to reach your origins directly — allowlist Cloudflare health-check IPs if the origin is firewalled.
